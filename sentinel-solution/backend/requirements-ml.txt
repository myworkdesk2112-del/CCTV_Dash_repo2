# Real detection/ANPR deps, kept separate from requirements.txt so the base
# service (registry, alerts, watchlist, API) installs fast and runs without
# a GPU/large downloads. Install these in the SAME venv as requirements.txt:
#
#   python -m venv .venv && .venv/Scripts/activate
#   pip install -r requirements.txt -r requirements-ml.txt
#
# Versions are pinned deliberately, not just "latest": paddleocr>=3.0 changed
# its public API (dropped `show_log=`, changed the .ocr() result shape) in a
# way that breaks analytics/anpr.py's PaddleOcrPlateReader — verified by
# actually installing 3.7.0 and hitting the incompatibility at runtime, not
# assumed. 2.9.1 is the version anpr.py's parsing logic was written against
# and verified against (see analytics/anpr.py's docstring / STRATEGY.md).
ultralytics==8.4.138     # YoloVehicleDetector (analytics/detector.py) — pretrained COCO weights (yolov8n.pt) work out of the box for car/truck/bus/motorcycle/person
lap==0.5.13              # required by ultralytics' built-in ByteTrack (model.track(...)) — pinned explicitly; ultralytics silently auto-installs this at runtime if missing, which is not something to rely on in a production/offline deployment
paddleocr==2.9.1         # PaddleOcrPlateReader (analytics/anpr.py) — pin matters, see above
paddlepaddle==2.6.2      # PaddleOCR's inference backend

# YoloPlateDetector (analytics/plate_detector.py) — real trained plate
# localizer, morsetechlab/yolov11-license-plate-detection (AGPL-3.0, see
# HLD.md §10 for the licensing decision). Loading the .onnx weight the
# first time triggers ultralytics' "requirements: AutoUpdate" behavior,
# which silently upgrades `onnx`/`onnxruntime` to versions that pull in
# protobuf>=4 — that BREAKS paddlepaddle 2.6.2 at import time
# (`TypeError: Descriptors cannot be created directly`), reproduced
# empirically, not theoretical. Pin all three explicitly so a fresh venv
# never hits ultralytics' auto-update path at all.
onnx==1.14.1
onnxruntime==1.17.3
protobuf==3.20.2

# KNOWN LIVE CONFLICT (found 2026-09-13): on this dev environment (Python
# 3.12), loading the plate-detector .onnx weights triggered ultralytics'
# AutoUpdate anyway, silently upgrading the venv to onnx==1.22.0 /
# protobuf==6.33.6. Attempting to re-pin back to onnx==1.14.1 failed outright
# on Python 3.12 -- that release predates cp312 wheel support and falls back
# to a source build requiring cmake (not installed here). Options were:
# (a) recreate the venv on Python <=3.11 so onnx==1.14.1's prebuilt wheel
# installs cleanly, (b) install cmake and build onnx==1.14.1 from source, or
# (c) find a newer onnx/onnxruntime/protobuf combination that both has
# cp312 wheels and is verified compatible with paddlepaddle==2.6.2.
#
# **Option (c) resolved 2026-09-26, verified on Python 3.12:**
#   onnx==1.23.0, onnxruntime==1.30.0, protobuf>=6.31.1
# (installed via `pip install ultralytics paddleocr==2.9.1 paddlepaddle==2.6.2`
# without repinning ultralytics first, which is why this resolved to
# ultralytics==8.4.163, not this file's ultralytics==8.4.138 pin — that
# version gap is not itself verified compatible/incompatible with the pin
# below; a fresh install following this file's own instructions, i.e.
# `pip install -r requirements.txt -r requirements-ml.txt` with the pin as
# written, was not what today's scans actually ran on.)
# `paddlepaddle` still hard-requires protobuf<=3.20.2 at import time
# (`base/proto/*_pb2.py` uses the old descriptor-pool API), so this is NOT a
# same-protobuf-version fix — it's running paddle's protobuf calls through
# the pure-Python implementation instead of upgrading/downgrading anything:
# set `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` in the environment
# before importing `paddleocr`/`paddle`. Verified: `YoloVehicleDetector`,
# `YoloPlateDetector` (real ONNX weights), and `PaddleOcrPlateReader` all
# construct and run real inference together in one process with this env
# var set (see `scripts/real_anpr_scan.py`'s invocation instructions below).
# The pure-Python protobuf path is slower per-call but this is OCR on
# small crops, not a hot loop — no observed effect on the 2026-09-26 scans.

# WINDOWS DLL ORDERING GOTCHA (verified empirically, not theoretical):
# importing paddleocr/paddlepaddle BEFORE torch in the same process corrupts
# torch's native DLL loading (`OSError: ... torch\lib\shm.dll ...`). Both
# ship their own OpenMP/MKL-family DLLs and the wrong one wins on Windows if
# paddle loads first. Always construct the YOLO detector (which imports
# torch) before the PaddleOCR reader — see main.py's `_detector`/
# `_plate_reader` module-level ordering and its comment. Only verified on
# Windows so far (this dev environment); not tested on Linux — if the
# production/demo box is Linux, re-verify whether this ordering constraint
# still applies before assuming it does or doesn't.
